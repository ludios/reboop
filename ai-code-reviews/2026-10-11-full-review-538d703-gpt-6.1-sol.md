Full review comments:

- [P1] Disable agent forwarding on reboop SSH connections — /home/at/code/system/reboop/src/ssh.rs:91-93
  **High severity, conditional on agent forwarding.** With `ForwardAgent yes` in the user's SSH configuration, a compromised checked machine can request the fixed `reboop-luks-v1` signature and derive the permanent password-encryption key. Using the VM's test key, I verified that signing through its forwarded agent produces exactly the locally derived signature. Any subsequently obtained encrypted password files become decryptable without further agent access. Force `ForwardAgent=no` on reboop connections, and document that the signing key must not be available through agents forwarded elsewhere.

- [P1] Exclude built-in tokens from password verification — /home/at/code/system/reboop/src/initrd.rs:92-92
  **High severity.** `--disable-external-tokens` does not disable cryptsetup's built-in `luks2-keyring` token. When its passphrase is available in the running machine's keyring, this command succeeds without checking the supplied password. I reproduced exit status 0 for an incorrect password using this exact command on cryptsetup 2.8.6. Reboop can therefore store or approve an invalid password, reboot, and become unable to unlock once the volatile keyring disappears. Force passphrase-only verification—for example, also use an unavailable token type with external tokens disabled—and add a keyring-token regression test.

- [P1] Discover every btrfs root member before checking LUKS — /home/at/code/system/reboop/src/initrd.rs:69-72
  **High severity for multi-device encrypted roots.** `findmnt` returns one btrfs member, and inverse `lsblk` follows only that member's block-device ancestry; it does not discover the other btrfs members. I verified this on the RAID1 VM: the traversal contains only vda although the filesystem also uses vdb. With separately encrypted members, the one-device guard can incorrectly pass while another member needs a different password; with an unencrypted first member, reboop can incorrectly decide nothing needs unlocking. Reuse btrfs member discovery, then validate every required LUKS device or reject unsupported layouts before rebooting.

- [P1] Verify initrd host-key trust before rebooting — /home/at/code/system/reboop/src/bounce.rs:218-221
  **High severity on a first encrypted bounce or after initrd key rotation.** Preflight verifies only the stage-2 SSH target. The initrd connection later enforces `StrictHostKeyChecking=yes`, but by then services are stopped and the machine has rebooted. If its distinct initrd host key is not trusted, unlocking fails and the machine remains unavailable. The VM harness pre-populates both host keys, masking this prerequisite. Validate trust for the upcoming initrd identity before stopping services, and document a verified key-enrollment procedure rather than relaxing host-key checking.

- [P2] Check configured GRUB mirrors even when their directories vanish — /home/at/code/system/reboop/src/boot.rs:291-293
  **Medium severity.** Discovery includes a boot path only when its `grub` directory currently exists. An unmounted mirror with an empty underlying directory, or a mirror that loses its entire `grub` directory, therefore disappears instead of becoming a blocker. I reproduced the omission by unmounting `/boot-fallback` inside an isolated VM mount namespace. The remaining primary entry can pass even though firmware booting the mirror would encounter stale files or no configuration. Obtain expected mirror paths from the NixOS boot-loader configuration and check each one; extend the VM test beyond deleting only `grub.cfg`.

- [P2] Prefer bootctl's effective command line over raw options — /home/at/code/system/reboop/src/boot.rs:90-90
  **Medium severity for UKIs with command-line addons.** Systemd's `bootctl` supplies both `options` and `cmdline`: the latter includes appended global and image-specific addon parameters. Preferring `options` discards those additions. An addon supplying another `init=` or a static `ip=` can consequently make the system or address checks approve something different from what will actually boot. Prefer `cmdline`, falling back to `options` for older output, and test a realistic entry containing both fields with different values.

- [P2] Compare postflight against the pre-reboot system snapshot — /home/at/code/system/reboop/src/bounce.rs:424-428
  **Medium severity when the system profile changes during startup.** Postflight compares the booted system and kernel against a freshly read profile, not the configuration approved before reboot. An automatic upgrade after startup can make a successful bounce fail because it correctly booted B but now compares against C; conversely, resetting the profile to an incorrectly booted A can conceal failure to boot the planned B. Preserve the expected system and kernel from the second preflight and pass them into postflight. Keep catch's no-preflight expectation policy separate.

- [P2] Verify the machine identity on the catch return path — /home/at/code/system/reboop/src/bounce.rs:347-352
  **Medium severity for an incorrect configured IPv4 address.** `check` and `bounce` verify the remote hostname through `preflight::gather`, but `catch` accepts this return path without that check. If the address points to another already-trusted NixOS machine, catch compares that machine against its own profile, scrubs it, and reports the requested hostname as back and healthy. Extract the existing hostname/FQDN validation and apply it when accepting a returned stage-2 session, including catch.

- [P2] Include initrd address validation in check's reboot verdict — /home/at/code/system/reboop/src/check.rs:27-29
  **Medium severity for encrypted machines with a mismatched static initrd address.** `preflight::blockers` never checks the boot entry's initrd addresses; that validation exists only in bounce's password path. Thus `reboop check` can report `okay_to_reboot: true` for a machine that bounce subsequently refuses, contrary to the advertised preflight behavior. This also makes check unsafe as the advertised eligibility check for external reboot automation. Put address validation in shared reboot-preflight logic and report it as a blocker, while preserving stop's intentional exemption.
