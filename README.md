# reboop

Reboots NixOS machines over SSH, carefully. `reboop bounce HOSTNAME`:

1. Refuses if the boot loader's default (systemd-boot's, or GRUB's in every mirrored /boot) wouldn't boot the system profile, lacks its kernel or initrd, or has the initrd take a static address (`ip=`) other than the machine's. Refuses if the machine is busy: a btrfs scrub (which would hang shutdown), balance or other exclusive operation, or a device that's missing or has had errors; a disk beneath a btrfs filesystem that SMART says is failing (a failed self-assessment, or reallocated, pending or uncorrectable sectors), where smartmontools is installed (one in standby isn't woken to check); a Nix command or build, or switch-to-configuration; a tmux server (unless the machine's `tmux` setting is `resume`: see below); a copy by rsync, cp, mv, scp, dd, ddrescue, pv or an rclone transfer such as `rclone copy` (doc/spec.md lists the transfers); a btrfs send or receive; cryptsetup; a disk tool such as fsck, mkfs, resize2fs, `btrfs check` or a partitioner (doc/spec.md lists them all); an inhibitor lock against shutdown (see `systemd-inhibit`); a systemd job that lasts 5 seconds or more; network traffic or load average over a limit; a root filesystem that's nearly full (97% by default). `reboop check` shows this for all machines without rebooting any, along with why each needs a reboot, if it does: the system profile isn't the active configuration (after `nixos-rebuild boot`), or has a new or rebuilt kernel, kernel modules or initrd compared with what booted, or a new or rebuilt systemd compared with the one PID 1 runs (switching re-executes it). It also shows whether `nixos-rebuild switch` or `boot` would change the system profile, which `bounce` warns about but goes ahead: it evaluates the toplevel of `<nixpkgs/nixos>`, with `nixos-config` from NIX_PATH (`nix.nixPath`), without building it (though it downloads sources the configuration fetches, like a rebuild would). That takes seconds, but can take a GB or more of the machine's RAM; `check_rebuild: false` turns it off.
2. If / is on LUKS, checks that the stored password still opens it.
3. Stops the machine's `stop_services` (e.g. PostgreSQL), checks again that it's okay to reboot (apart from load and network traffic, which stopping services changes), and reboots. If it's no longer okay, it leaves the services stopped and says so.
4. Unlocks LUKS (if any) by SSHing into the systemd initrd.
5. Once booted, shows kernel errors, failed units, and whether the expected NixOS system and kernel came up; then brings back what was in tmux, if the machine's `tmux` setting is `resume` (see below).
6. Scrubs btrfs, failing loudly on errors, unless a scrub found the filesystem clean less than `scrub_every_days` (14 by default) days ago, and `btrfs scrub status` agrees that the latest scrub finished clean. It remembers the scrubs it saw in `/var/lib/reboop/last-clean-scrub/` on the machine, in a file named by the filesystem's UUID whose modification time is when one last finished clean; one that doesn't removes it. Delete the file to get a scrub at the next bounce, or touch it to put one off.

`reboop catch HOSTNAME` does steps 4 to 6 for a machine that was rebooted some other way, like by hand or by a power cut, or whose bounce was cut short. If the machine is already up, it checks the boot it's in.

`reboop stop HOSTNAME` does steps 1 and 3 with a shutdown (`systemctl poweroff`) in place of the reboot, then waits for the machine to stop accepting SSH. It leaves out what's only for unlocking afterwards: step 2, and step 1's check of the initrd's address.

With `"tmux": "resume"` among a machine's settings (the default, `"block"`, is what step 1 says), reboop saves what's in the machine's tmux servers right before taking it down, and brings it back once the machine is up again: every session, window and pane, with the directory the pane's command was started in and what the pane is running, which it knows as typed from the zsh-spy archive that the pane's zsh holds open. A command is run again only if one of the machine's `resumable_commands` matches it: regular expressions (the Rust regex crate's), each of which has to match the whole command line, so `"yt-dlp .*"` rather than `"yt-dlp"`; those in defaults.json apply to every machine, and a machine's own are added to them. A command that's a reason not to reboot in its own right, like a copy or a Nix build (see step 1), keeps the machine up however it's matched. A pane started with a command rather than a shell (`tmux new-window 'sleep 600'`) is matched as tmux shows that command, quoted for its own parser, as `"sleep 600"` with the quotes. A pane running anything else keeps the machine from going down, as does a pane whose command can't be known (its shell has no zsh-spy archive, HIST_IGNORE_SPACE hid the line, a program replaced the shell, or the shell has a child process its archive doesn't account for, like a disowned job), a pane whose shell has a background job still running, a typed or started command whose directory is gone, and a server that can't be listed (as when its tmux is another version than the machine's, or it's in a container's network namespace). Idle panes just come back idle. Since a command runs again in a fresh shell, from the start, variables and functions set by hand in the old shell are gone, as is the pane's scrollback, so only commands that can start over belong in `resumable_commands`; `reboop tmux list` shows what would be run again.

To bring it all back, once systemd has finished starting up, reboop waits up to 10 minutes for any `mount` still running to finish (such as those of a script that mounts filesystems in parallel), starts a tmux server for each user from a transient unit that logs them in through PAM (so the server lives in a logind session of theirs, with a login's environment, as one left behind by logging out would), recreates their sessions with the windows' names, layouts, and active window and pane, and types each command into a fresh shell of the user's in the pane's directory (with bracketed paste and Enter, so that zsh-spy records it again), once that shell is at its prompt, in that very directory, with the directory on the filesystem mounted where it was; a pane started with a command gets that command again. Every look at the servers, by `reboop check`, `reboop tmux list`, or a `bounce` or `stop` that gets as far as taking the machine down, is saved on the machine in `/var/lib/reboop/tmux/` (the last 200 of them, and the pending one, for root only, as they hold other users' command lines), where `bounce`, `stop` and `reboop tmux stop` also point `pending` at theirs, for the postflight (or `catch`, or `reboop tmux start`) to bring back, forgetting the link first so that a restore cut short isn't repeated on top of itself; a pending capture taken for a reboot or shutdown in the current boot means the machine never went down, so it's forgotten without being brought back. `reboop tmux list HOSTNAME` shows what's in the servers and what's resumable; `reboop tmux stop HOSTNAME` saves it and kills the servers (whose processes get SIGHUP, as on closing a terminal), refusing if a pane's command isn't resumable or a server can't be listed, whatever the machine's `tmux` setting, for `reboop tmux start HOSTNAME` to bring back, e.g. around upgrading tmux. `--saved FILE` makes `list` or `start` take a capture saved on the machine instead, like the last check's after a crash.

LUKS passwords are stored in `~/.config/reboop/luks/`, encrypted with a key derived from an `ssh-keygen -Y sign` signature, so they're usable wherever your Ed25519 or RSA SSH key is. reboop connects only to hosts whose keys are already in known_hosts, whatever your ssh config says: the machine's, under its `ipv4` (`[ipv4]:port` if its `ssh_port` isn't 22), and for LUKS, its initrd's, under `[ipv4]:initrd_ssh_port`. Machines and limits go in `~/.config/reboop/defaults.json` and `machines.jsonl`; see [doc/spec.md](doc/spec.md).
